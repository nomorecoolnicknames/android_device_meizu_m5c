# M5C tearing lane — разрывы изображения (стежок между двумя моментами движения)

Дата: 2026-08-27. Устройство 710HVBR923RYK, LOS 14.1, ядро 4.9.188-m5c+,
панель ILI9881c 720×1280 @ 58.46 Гц (vsyncFPS=5846 от ядра), forge_hwc
(HWC1.1, HW-оверлеи). Симптом: при скролле горизонтальный «стежок» между
двумя моментами движения, граница гуляет в районе 40–90 % высоты,
одинаково с оверлеями и без (p80).

## Вердикт

**FACT: разрыв запечён продюсером (hwui) в буфер ещё до `queueBuffer`.**
Механизм: hwui работает в `SwapBehavior::Preserved`
(`Swap behavior 1` в logcat всех процессов — блоб Mali-T720 не даёт
`EGL_EXT_buffer_age`), т.е. рисует **частично** — только damage-регион —
поверх якобы сохранённого заднего буфера. Блоб **принимает**
`eglSurfaceAttrib(EGL_SWAP_BEHAVIOR, EGL_BUFFER_PRESERVED)` (ни одного
«Failed to set EGL_SWAP_BEHAVIOR» в logcat), но фактически содержимое
не сохраняет: dequeue по кольцу из 3 буферов отдаёт буфер возрастом
2–3 кадра, а hwui при `Preserved` безусловно считает возраст = 1
(`EglManager::queryBufferAge`). Итог: свежий damage ложится на основу
двух-трёхкадровой давности → в одном буфере два момента движения →
стежок на стекле. Не «подтверждение на глаз», а инструментальное:

FACT (forge-shear проба, скролл Настроек скриптом, `debug.forgehwc.shear=1`,
HWC md5 4b1e5d85…/4f79757c…):

```
итог: frames=1152 motion=751 zoned=749 hard=39   (~5 % кадров движения)
здоровый кадр:  map 88-160=0 328-1256=-151        (шапка на месте, тело одним блоком)
HARD-кадры:     seq=945  88-160=0 512-512=-101 824-824=-81
                seq=1042 88-128=0 712-712=-91 1024-1024=-71
                seq=1094 88-128=0 448-448=-52 1008-1008=-26
                seq=1141 88-128=0 864-864=-83 1176-1176=-63
```

Два РАЗНЫХ ненулевых сдвига строк внутри одного отправленного буфера =
содержимое из двух моментов скролла в одном кадре. Буфер к моменту чтения
уже отдан дисплею, acquire-fence отработан, а CRC-проба ранее доказала,
что после подачи в буфер никто не пишет, — значит, стежок был в буфере
уже на `queueBuffer`.

## Починено

1. `frameworks/base/libs/hwui/Properties.h`:
   `PROPERTY_ENABLE_PARTIAL_UPDATES` переименован
   `debug.hwui.enable_partial_updates` → **`debug.hwui.partial_updates`**.
   FACT: имя AOSP — 33 символа при лимите bionic в 31 (`setprop` отвечает
   «name too long»), т.е. штатную ручку на N вообще невозможно установить.
2. `device/meizu/m5c/system.prop`: **`debug.hwui.partial_updates=false`**
   (hwui всегда рисует полный кадр — `SwapBehavior::Discard`).
   Убрана мёртвая строка `debug.hwui.render_dirty_regions=false`:
   FACT — такого свойства в hwui ветки N нет (grep по Properties.{h,cpp},
   EglManager.cpp пуст), ручка эпохи M, не работала с самого Init-коммита.
3. `hwcomposer/forge_hwc.c`: закоммичена shear-проба (детектор разрывов,
   уже запечённых в отправленный буфер: посрочные сигнатуры plane 0,
   сопоставление соседних кадров по вертикальным сдвигам ±160 строк,
   `debug.forgehwc.shear=N`; плюс kmsg-маркеры forge-nofence/forge-pitch).
   Standalone-сборка этой пробы стоит на устройстве.

## Что пересобрать

- **libhwui** (`frameworks/base/libs/hwui`) — чтобы жило новое имя
  свойства; без этого `debug.hwui.partial_updates` ничего не выключает.
- **build.prop** из system.prop устройства (собирается вместе с ROM).
- Идущая `mka bacon` подхватит правки, только если libhwui ещё не
  скомпилирован; иначе после её конца — `mka libhwui` + пересборка образа.

Проверка после прошивки (объективная, без глаз):
`setprop debug.forgehwc.shear 1`, скролл Настроек ~30 с →
`dmesg | grep forge-shear`: ожидание `hard=0` (при
`debug.hwui.partial_updates=false`); контрпроба — `setprop
debug.hwui.partial_updates true` + `am force-stop com.android.settings`,
тот же скролл → HARD-кадры должны вернуться. Это последний недостающий
шаг доказательства (A/B на самой ручке); всё остальное уже FACT.

## Гипотезы и вердикты

| # | Гипотеза | Вердикт | Улика |
|---|----------|---------|-------|
| 1 | HWC не отдаёт SF vsync (callback/период/фаза) | REJECTED | В `forge_hwc.c` vsync-поток на `DISP_IOCTL_WAIT_FOR_VSYNC` + `procs->vsync()` с меткой ядра; `eventControl` есть; dumpsys: `DispSync refresh 17105713ns` == периоду HWC (vsyncFPS=5846), `mDebugForceFakeVSync=0`. Главное: при латче конфига в бланкинге (доказано ядерным лейном) НИКАКАЯ ошибка тайминга SF не может дать стежок — только джанк. |
| 2 | Неверный `HWC_DISPLAY_VSYNC_PERIOD` | REJECTED | Период 17105713 нс = 58.46 Гц ядра; SF, HWC и ядро согласованы; и см. аргумент атомарного латча выше. |
| 3 | Двойная буферизация FBT (`NUM_FRAMEBUFFER_SURFACE_BUFFERS`), буфер уходит на скан до конца отрисовки | REJECTED | Разрыв одинаков с оверлеями (fbt=0, ovl_frames=2535/2538 — FBT вообще не в тракте) и без; release-фенсы честные (журнал 2026-08-27: `_ovl_fence_release_callback` после frame-done). |
| 4 | Продюсер дописывает в отданный буфер (ранний release/лживый mali-fence) | REJECTED | Журнал de48969: acq-фенсы честные (waited=32, avg 6.9 мс, max 19 мс), CRC 246 прогонов dirty=0; чтение ядра: релиз после frame-done. |
| 5 | RDMA FIFO underflow (OVL0_INTSTA 0xe03 при 3 плоскостях) | REJECTED (как источник стежка) | Это отдельный артефакт «рассыпание к низу кадра»; стежок из двух моментов движения требует содержимого двух кадров и виден и при одной плоскости (p80). |
| 6 | hwui рисует частично поверх несохранённой основы (Preserved swap сломан в блобе) | **CONFIRMED** | shear: 39 HARD из 1152, два разных ненулевых сдвига в одном буфере; `Swap behavior 1`; блоб принимает PRESERVED без ошибок, но основа устаревшая. |

## Осталось

- A/B на самой ручке после пересборки libhwui (см. выше) — финальное
  подтверждение и контроль регрессии.
- Опционально: вернуть частичную отрисовку, если найдётся способ заставить
  блоб честно сохранять буфер (маловероятно, блоб 2016 г.).
- `debug.forgehwc.shear` держать 0 в обычной жизни (проба читает ~3.5 МБ
  на кадр).
