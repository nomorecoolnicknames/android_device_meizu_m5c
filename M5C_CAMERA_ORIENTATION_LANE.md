# M5c — лента «камера повёрнута на 180°»

Отдельная линия работ: и видоискатель, и сохранённые снимки перевёрнуты на 180°
(подтверждено владельцем, 2026-08-17). Цвет (радужные пятна / отсутствие OTP)
— **другая** линия, её ведёт отдельный агент; здесь цвет не трогаем.

Дата: 2026-08-17. Устройство: `710HVBR923RYK`, LOS 14.1 (userdebug, SELinux
Permissive, adb-shell = root `u:r:su:s0`).

## 1. Идентичность артефактов

FACT: `mediaserver` (pid 376) — это процесс, в котором живёт `CameraService`;
отдельного `/system/bin/cameraserver` в этой сборке нет.

FACT: в `/proc/376/maps` подгружены **32-битные** библиотеки
`/system/lib/libcameracustom.so` и `/system/lib/libcam.halsensor.so`
(адреса `f2c43000`, `f0b26000`). 64-битные копии в `/system/lib64/` присутствуют,
но mediaserver их не загружает.

FACT: размеры на устройстве совпадают с копиями в дереве байт-в-байт:

| файл | размер | md5 (в дереве) |
|---|---|---|
| `vendor/meizu/m5c/proprietary/lib/libcameracustom.so` | 16866932 | `d4b5c4b1b34b13285edaff50fe45858c` |
| `vendor/meizu/m5c/proprietary/lib64/libcameracustom.so` | 17138288 | `6c6901b416d6e2b457f50ab1cd169872` |

## 2. Что фреймворк сообщает приложениям (ground truth)

FACT (`adb shell dumpsys media.camera`, 2026-08-17):

```
Camera module HAL API version: 0x100
Number of camera devices: 1
Camera 0 information:
  Facing: BACK
  Orientation: 90
  Device version: 0x100
  Camera1 API shim is using parameters: ...
```

Т.е. приложениям (`org.cyanogenmod.snap` в списке prior clients) отдаётся
`CameraInfo.orientation = 90`, камера ровно одна — только main. Фронтальный
S5K5E8YX не перечисляется вообще.

INFERENCE: одна ошибка в 180° в этом значении объясняет **оба** симптома сразу.
Camera1-приложение считает поворот превью как `(orientation - display_rotation)`
и поворот JPEG как `(orientation + display_rotation)`; если реально нужно 270, а
отдаётся 90, и превью, и снимок уезжают ровно на 180°. Согласуется с тем, что
снятый кадр `IMG_20260817_151905.jpg` — портретный 1920x2560, т.е. HAL честно
повернул его на объявленные 90°.

## 3. Откуда берётся это число

FACT: единственный потребитель символа — `lib/libcam.halsensor.so`:

```
nm -DuC lib/libcam.halsensor.so | grep NSCamCustomSensor::getSensorOrientation
```

даёт совпадение, и **больше ни один** блоб в `vendor/meizu/m5c/proprietary` этот
символ не импортирует.

FACT: `NSCamCustomSensor::getSensorOrientation()` в `libcameracustom.so` — это
заглушка из двух инструкций, возвращающая адрес const-структуры в `.rodata`:

```
arm    0x00101f74:  ldr r0,[pc,#4]; add r0,pc; bx lr
       литерал 0x00c9379e + pc 0x00101f7a      -> vaddr 0x00d95718
       .rodata Addr 0x001046f0 / Off 0x000fe6f0 -> файловое смещение 0x00d8f718
arm64  0x0014e484:  adrp x0,0xde1000; add x0,x0,#88; ret
                                                -> vaddr 0x00de1058
       .rodata Addr 0x0014f930 / Off 0x0012d930 -> файловое смещение 0x00dbf058
```

FACT: по обоим смещениям лежат одинаковые 16 байт
`5a000000 0e010000 5a000000 00000000`, т.е. `SensorOrientation_T` =
`{ main = 90, sub = 270, main2 = 90, unused = 0 }`. Поле `main = 90` совпадает с
тем, что показал `dumpsys`, поле `sub = 270` — обычная пара MTK для фронталки.

FACT: `NSCamCustomSensor::isRetFakeSubOrientation()` /
`isRetFakeMainOrientation()` (ICF-слитые в один адрес) возвращают `0`
(arm64: `mov w0,#0; ret`). Никакого «поддельного» пути ориентации не включено.

FACT (отрицательный результат): свойства (property), которым можно было бы
переопределить это значение, **нет**. Поиск по строкам всех `.so` в
`vendor/meizu/m5c/proprietary` на шаблон
`(ro|persist|debug|mtk)\.[...](orient|rotat)[...]` даёт единственное попадание —
`ro.sf.hwrotation`, а это поворот всего SurfaceFlinger, а не камеры.
REJECTED: «поправим prop и не будем трогать блоб» — переопределять нечего.

FACT: в `device/meizu/m5c` нет ни одного упоминания ориентации камеры
(`grep -rniE "orientation|hwrotation|rotat"` даёт только тач-матрицу в
`BRINGUP_STATE.md`, `bin/orientationd` в списке блобов и `screenOrientation` в
манифестах EngineerMode/YGPS). В дереве ROM нет `vendor/mediatek` — исходников
mtkcam/`libcameracustom` у нас нет, только прибилды.

## 4. Ядерная сторона: сенсор уже перевёрнут драйвером

FACT (`/home/valakas/m5c/android_kernel_meizu_m5c/drivers/misc/mediatek/imgsensor/src/mt6735m/`):

| драйвер | `.mirror` | `sensor_output_dataformat` | вызов |
|---|---|---|---|
| `s5k4h8_mipi_raw/s5k4h8mipi_Sensor.c` (main) | `IMAGE_HV_MIRROR` (стр. 231) | `SENSOR_OUTPUT_FORMAT_RAW_Gb` (стр. 216) | `set_mirror_flip(IMAGE_HV_MIRROR)` жёстко во **всех** режимах (стр. 4397, 4445, 4463, 4484, 4504) |
| `s5k5e8yx_mipi_raw/s5k5e8yxmipiraw_Sensor.c` (sub) | `IMAGE_NORMAL` (стр. 173) | `SENSOR_OUTPUT_FORMAT_RAW_Gr` (стр. 161) | `set_mirror_flip(imgsensor.mirror)` |

FACT: `set_mirror_flip()` в S5K4H8 пишет `0x0101 = 0x03` для `IMAGE_HV_MIRROR`
(собственный комментарий драйвера помечает этот случай как «Gb»), а `0x00` для
`IMAGE_NORMAL` — «Gr». То есть объявленный порядок Байера **согласован** с
включённым H+V зеркалом: драйвер внутренне непротиворечив.

INFERENCE: H+V зеркало математически тождественно повороту на 180°. Значит поток,
который HAL реально отдаёт для camera 0, повёрнут на 180° относительно того, что
описывает `main = 90`. Правдивое значение для доставляемого потока — **270**.
Контракт Android как раз про доставляемое изображение: `CameraInfo.orientation` —
это «угол, на который нужно повернуть кадр по часовой, чтобы он смотрелся верно
на экране в его естественной ориентации», а не описание кристалла.

## 5. Противоречие и три гипотезы

Противоречие, названное явно: `libcameracustom.so` — блоб **стокового Flyme**
этого же устройства, и он говорит `main = 90`. Если на стоке камера была ровной,
то одно из звеньев у нас отличается от стока.

- **H1 (HYPOTHESIS)**: стоковый драйвер S5K4H8 у Meizu **не** включает
  `IMAGE_HV_MIRROR` (значит и `dataformat` там `RAW_Gr`), а наш порт взял
  референсный MTK-вариант с зеркалом. Тогда «настоящий» корень — в ядре, а
  правка в userspace лишь компенсирует.
  Falsify: снять стоковое ядро (в recovery-разделе живёт TWRP, собранный на
  стоковом ядре 3.18.19) и в его дизассемблере найти запись `0x0101` в
  mode-функциях S5K4H8: `0x03` → H1 REJECTED, `0x00` → H1 подтверждена.
  **Артефакт отсутствует**: стокового `boot.img`/исходников m5c на build station
  нет (`/home/valakas/m5c/*.img` — все наши сборки; `decompiled_src/` пуст),
  поэтому H1 сейчас не проверяема. Не заметаем под ковёр: это открытый вопрос.
- **H2 (HYPOTHESIS)**: стоковое userspace Meizu (`MZCameraService` / штатное
  приложение камеры) само добавляло 180°, а таблица `{90,270,90}` — просто
  нетронутый референсный дефолт MTK. В пользу: пара `{90,270}` — ровно
  учебный дефолт MTK, следов тюнинга под m5c в таблице нет.
  Falsify: посмотреть в стоковом APK/`MZCameraService`, есть ли добавка поворота.
- **H3 (REJECTED)**: «блоб не от m5c, а от другого Meizu». Отвергнуто:
  размеры файлов на устройстве совпадают с копиями в дереве, а сам блоб знает
  именно наш комплект сенсоров (`SENSOR_DRVNAME_S5K5E8_ST_MIPI_RAW` в логах
  запроса `queryCustCamfeature`), т.е. это конфиг под этот аппарат.

Важное следствие для выбора правки: H1 и H2 обе оставляют геометрию одинаковой,
и **любая** из двух правок (снять зеркало в ядре / сказать правду в метаданных)
делает кадр ровным. Но правка в ядре — это **две** связанные правки
(`.mirror` → `IMAGE_NORMAL` **и** `dataformat` → `RAW_Gr`), иначе поедет порядок
Байера и сломается цвет — а цветовая линия сейчас в работе у другого агента, и
дерево ядра принадлежит другим агентам. Правка метаданных — одно 32-битное
значение, ноль влияния на пиксельный путь.

## 6. Правка

Смысл: `main` 90 → 270 в `SensorOrientation_T`. `sub` уже 270 и трогать его
**не надо** (фронтальный драйвер зеркало не включает); `main2` не существует
физически (`Number of camera devices: 1`), оставлен как есть.

Инструмент, чтобы правка была воспроизводимой и рецензируемой, а не «кто-то
подправил байтик в блобе»:

```
device/meizu/m5c/patch_camera_orientation.py            # выводит и правит таблицу
  ./patch_camera_orientation.py --check <lib>           # только показать
  ./patch_camera_orientation.py --main 270 <lib>        # применить (идемпотентно)
```

Скрипт находит файл по размеру, проверяет, что по смещению лежат осмысленные
градусы, и отказывается работать иначе. Обратная правка — `--main 90`.

Результат на 32-битной копии (та, которую грузит mediaserver):
`{ main=270, sub=270, main2=90, unused=0 }`, md5
`888e060fa07af624f9cf7bb95ab0239a` (было `d4b5c4b1b34b13285edaff50fe45858c`).

### Живая проверка (без пересборки ROM)

Патченный файл уже лежит на девбоксе: `/tmp/libcameracustom.arm.main270.so`.
Прошивку/запись в `/system` делает родительская сессия; команды (каждая —
отдельный вызов `dev.sh`, он ломает `;` внутри строки):

```sh
D=/home/n8n/.claude/skills/devbox/scripts/dev.sh
S=710HVBR923RYK
$D adb -s $S shell "mount -o rw,remount /system"
$D adb -s $S shell "cp /system/lib/libcameracustom.so /data/local/tmp/libcameracustom.so.orig"
$D adb -s $S push /tmp/libcameracustom.arm.main270.so /system/lib/libcameracustom.so
$D adb -s $S shell "chmod 644 /system/lib/libcameracustom.so"
$D adb -s $S shell "setprop ctl.restart media"
$D adb -s $S shell "dumpsys media.camera" | grep -i Orientation
```

Ожидаемое доказательство: `Orientation: 270` вместо `90`, после чего владелец
открывает камеру — превью ровное, снимок ровный. Откат: положить назад
`/data/local/tmp/libcameracustom.so.orig` (или просто перепрошить `system`).

Разрешающий эксперимент внутри той же проверки: если `dumpsys` покажет
**всё ещё 90**, значит HAL читает не поле 0, а поле 2 (`main2`) — тогда
`--main2 270` и повтор. Поле 0 как `main` — соглашение MTK, а не наш замер:
наблюдаемые 90 стоят и в поле 0, и в поле 2, различить их можно только этим
опытом.

### Постоянная правка

После подтверждения на железе — применить тот же скрипт к обеим копиям в дереве:

```sh
python3 device/meizu/m5c/patch_camera_orientation.py --main 270 \
  vendor/meizu/m5c/proprietary/lib/libcameracustom.so \
  vendor/meizu/m5c/proprietary/lib64/libcameracustom.so
```

64-битную копию правим для симметрии, хотя mediaserver её не грузит (FACT §1):
рассогласованная пара блобов — мина для будущего разбора.

Сознательно **не сделано до подтверждения**: коммит правленого 17-МБ блоба
необратимо ложится в историю git, а значение ещё не проверено на железе.
Закоммичены сейчас только этот документ и скрипт.

### Компромиссы и альтернативы

- **Правка `.rodata` в прибилде** (выбрано). Плюсы: одно 32-битное значение, ноль
  кода, ноль релокаций, ноль влияния на другие линии (цвет, фонарик).
  Минусы: правка живёт в бинарнике — при повторном `extract-files.sh` она
  затирается. Митигация: скрипт в дереве + эта запись.
- **Правило сборки**: держать блоб в git нетронутым, а патч применять во время
  сборки в промежуточную копию. Чище по git-истории, но требует убрать штатный
  `PRODUCT_COPY_FILES` для этой библиотеки из `m5c-vendor-blobs.mk` и завести
  генерируемый модуль — больше подвижных частей и обязательная полная сборка ROM
  для проверки.
- **`CameraWrapper` (канонический приём LOS)**: свой `camera.mt6737m.so` в
  device tree, который `dlopen`-ит переименованный вендорский модуль и правит
  `camera_info.orientation`. Устойчив к переизвлечению блобов, но требует
  переименования блоба в `proprietary-files-mtk.txt` + перегенерации
  vendor-`.mk`, для 32 и 64 бит, и корректной проброски всех полей
  `camera_module_t` (включая `set_torch_mode` и `get_vendor_tag_ops`). Прямо
  сейчас фонарик и камера в активной работе других агентов — вносить туда HAL-шим
  значит добавить риск на чужие линии. Держим как план Б, если правку блоба
  начнёт затирать переизвлечение.
- **Правка `frameworks/av`** отвергнута: дерево ROM общее с m681, глобальная
  подмена ориентации сломает другой аппарат.

## 7. Фронтальная камера

FACT: `Number of camera devices: 1` — фронталка сейчас не перечисляется вообще,
проверить её ориентацию нечем. FACT: её драйвер (`S5K5E8YX`) зеркало не включает
(`IMAGE_NORMAL` + `RAW_Gr`), а таблица уже отдаёт для неё `sub = 270`.
INFERENCE: править `sub` не требуется; когда фронталка заведётся, значение
надо перепроверить (для фронталки нормальный дефолт как раз 270).

## 8. Открытые вопросы

1. H1 непроверяема без стокового ядра m5c. Нужен артефакт: стоковый `boot.img`
   (или дамп раздела `recovery` с TWRP на стоковом ядре) — тогда видно, писал ли
   сток `0x0101 = 0x03`. Пока это не сделано, «правка в ядре была бы правильнее»
   остаётся HYPOTHESIS, а не FACT.
2. Поле `main2` оставлено равным 90; после подтверждения поля 0 это безвредно
   (второго сенсора нет), но если когда-нибудь появится dual-cam конфиг —
   пересмотреть.
